     DB layer (src/db/database.py)

     - Read-only, two layers: open the file as
       sqlite:///file:{path}?mode=ro&uri=true (SQLite refuses writes at the
       file level) and add a SQLAlchemy connect event that runs PRAGMA 
       query_only = ON (the rule in CLAUDE.md). Fails
       fast if the DB file doesn't exist (tells you to run python -m 
       src.db.build_db).
     - schema_as_text(engine) uses sqlalchemy.inspect: get_table_names,
       get_columns, get_pk_constraint,
       get_foreign_keys, get_unique_constraints, get_check_constraints. No table
       names in code.
     - run_query(engine, sql) → QueryResult(columns: list[str], rows: 
       list[tuple]) (small dataclass), using
       text(sql). Errors propagate as exceptions; the node catches them.

     Config (config/university_notes.md)

     Plain markdown, loaded once by path in main.py and passed into build_graph.
     Contents (draft):
     - Grades are numeric 0-100, stored on enrollments.grade.
     - Pass mark is 60: grade >= 60 passes, grade < 60 fails.
     - grade IS NULL means "not graded yet" (course still running). Exclude 
     NULLs from averages and pass/fail
       counts, and never treat NULL as 0.
     - The current semester is 'Fall 2026' (semesters.name). "This semester" / 
     "currently" means Fall 2026.
     - Semester names look like 'Fall 2025', 'Spring 2026'.
     - Names are not unique (two students can share a name); use ids to tell 
     people apart and mention it.
     (SQLite's inspector doesn't return the -- comments from schema.sql, so
     meaning lives here.)

     How the schema text looks in the prompt

     Generated, compact, one block per table:
     Table courses
       id INTEGER PK
       code TEXT NOT NULL UNIQUE
       title TEXT NOT NULL
       credits INTEGER NOT NULL
       department_id INTEGER NOT NULL -> departments.id
       CHECK (credits > 0)

     Table enrollments
       id INTEGER PK
       student_id INTEGER NOT NULL -> students.id
       offering_id INTEGER NOT NULL -> course_offerings.id
       grade REAL NULL
       UNIQUE (student_id, offering_id)
       CHECK (grade BETWEEN 0 AND 100)
     ...
     The generate_sql prompt is then: role + "Write one SELECT in the {dialect}
     dialect, return only SQL" + ## Schema (above) +
     ## Business rules (notes file) + ## Question. Model output is plain text; a
     tiny extract_sql() strips
     ``` fences. (Plain text instead of with_structured_output so the later
     fake-LLM tests stay trivial.)
     {dialect} comes from engine.dialect.name (e.g. sqlite) — no database name
     is hard-coded in prompts or code.

     State (src/agent/state.py)

     question: str, steps: list[str], step_index: int, sql: str, error: str | 
     None, attempts: int, results: Annotated[list[dict], operator.add], answer: 
     str, status: str.
     results uses an operator.add reducer, so nodes return only the new entries
     and LangGraph appends them.
     initial_state(question) sets steps=[question], step_index=0, attempts=0, 
     results=[], error=None, status="running" — so in milestone 4 the planner
     simply replaces how steps gets filled.
     Each entry in results: {"step", "sql", "columns", "rows"}.

     Graph (src/agent/graph.py)

     START → generate_sql → execute_sql → answer → END, linear edges.
     build_graph(llm, engine, notes) binds dependencies with functools.partial,
     so later tests pass a fake LLM and a
     test DB without patching. Schema text is computed once in build_graph, not
     per call.

     Nodes (each returns only the keys it changes):
     - generate_sql → {"sql"} — prompt with schema + notes + steps[step_index].
     - execute_sql → success: {"results": [entry]} (reducer appends); failure:
       {"error": str(exc), "status": "error"}.
     - answer → {"answer", "status"} (see below).

     How the answer node stays grounded in real results

     1. No LLM when there's nothing real to use: if error is set → fixed message
        ("I couldn't run the query: …",
        status error). If the result has 0 rows → fixed "The query returned no
        matching records." (status done).
        The model can't invent an answer from nothing.
     2. Only the results + the rules to read them: the prompt contains the
        question, the SQL that ran, the rows as
        a small markdown table (column headers from QueryResult.columns), and
        the university notes (so it reads a
        NULL grade as "not graded yet" and knows the pass mark is 60). The
        schema is not passed, so it has no
        material to reason beyond the data. Large results: first 50 rows shown
        plus "showing 50 of N rows".
     3. Explicit rules in ANSWER_PROMPT: answer only from the table; copy
        numbers exactly (no recomputing or
        rounding beyond 2 decimals); if the table doesn't answer the question,
        say so; don't mention data not in the
        table; temperature 0.
     4. The SQL and rows stay in state, so the CLI prints them next to the
        answer and a human can check it
        (tracing in a later milestone builds on this).

     CLI (src/main.py)

     load_dotenv() → connect_readonly(DEFAULT_DB_PATH) (reuse from
     src/db/build_db.py) → read notes →
     build_graph(get_llm(), engine, notes).invoke(initial_state(question)) →
     print SQL, row count, answer.
     Usage error if no question argument.

          Check printed SQL against the answer by hand.
     3. Export the session to docs/agent-sessions/02-minimal-graph.txt (check
