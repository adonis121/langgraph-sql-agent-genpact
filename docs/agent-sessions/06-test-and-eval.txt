     How results are compared (src/eval/compare.py)

     The agent's result = the last accepted step (state["results"][-1]); for
     multi-step
     questions that is the final step. Not "done" (give_up, decline,
     clarification) = fail with
     the status as reason.

     1. Normalize values: numbers -> round(float(x), 2) (so 57 == 57.0, 85.1666
        == 85.17);
        strings stripped; NULL stays None.
     2. Empty reference: pass iff the agent result is empty (is_empty_result: no
        rows or one
        all-NULL row) - so AVG -> NULL and zero rows both count.
     3. Columns - names and order ignored, extra columns allowed: the reference
        returns only the
        columns that define a correct answer (e.g. student id, grade). The agent
        usually adds more
        (names, titles, emails). We try every way to pick k agent columns for
        the k reference
        columns (itertools.permutations, at most a few hundred for <=7 columns)
        and pass if any
        projection gives the reference rows. Column names are never compared
        (avg_grade vs
        AVG(e.grade) don't matter).
     4. Rows - order ignored, compared as sets after projection: extra agent
        columns can change
        granularity (one row per failure vs one per student), and distinct
        projected rows handle
        that. No eval question asks for an order (no "top 3"), so there's no
        ordered mode.
     5. Fail reasons are specific: "status=error", "agent result has 2 columns,
        reference needs 3",
        "expected empty, got 4 rows", "no column mapping matches: 15 distinct
        rows vs 16 expected".

     Known limits (written in the report): rounding to 2 decimals (an agent that
     rounds to 1 fails);
     string values must match exactly (code "CS301" vs title "Databases" are
     different columns, so
     the reference picks the column the planner rule makes the agent return:
     ids, or codes).

     Runner (python -m src.eval)

     - load_dotenv, load_settings, connect_readonly, build_graph(get_llm(), ...)
       - same as src/main.py.
     - Per question: run reference SQL; run the agent through run_traced (so
       each eval run has a
       trace in traces/) with ask_user=lambda q: "" (non-interactive: a
       clarification ends in
       decline -> counted as a fail); compare.
     - Prints one line per question (PASS/FAIL, id, question, reason), then
       Score: 9/10 and the
       failed questions with reasons.
     - Writes docs/eval-report.md: date, model, score, a short "how results are
       compared"
       section, a table (id, covers, pass/fail, reason), and for each failure:
       question, agent SQL,
       first rows of the agent result, reference SQL, trace path.
       Self-contained, because
       traces/*.jsonl are git-ignored.

  How results are compared when the columns or row order differ
  (src/eval/compare.py)
  1. Values: numbers are rounded to 2 decimals, so 57 equals 57.0 and 85.1666
     equals 85.17. Strings are stripped of spaces.
  2. Columns: names are never compared, and the agent may return extra columns.
     The reference returns only the columns that make an answer correct, for
     example student id and grade. The comparison tries every way of picking
     agent columns for those reference columns and passes if any choice gives
     the reference rows.
  3. Rows: order is ignored, and rows are compared as sets after picking the
     columns. Extra agent columns can change how many rows there are (one per
     failure versus one per student), and picking the reference columns first
     takes care of that.
  4. Empty answers: an empty reference needs an empty agent result, meaning no
     rows or one row of only NULLs.
  5. Failed runs: a run that ends in give_up, decline or a clarification fails.

  There are two known limits: values must match exactly after rounding, and the
  comparison doesn't check the answer text, only the final step's rows.
