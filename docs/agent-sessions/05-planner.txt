     State (src/agent/state.py)

     Add two keys (and update the state list in CLAUDE.md):
     - plan: dict | None — the planner's structured output {decision, reason, 
       steps, clarifying_question}; stored whole so it shows in the trace.
     - clarification: str | None — the user's reply to the clarifying question.
       question stays the original text (traceability).

     - status gains "rejected" and "needs_clarification".

     Planner (nodes.plan)

     - Structured output without with_structured_output. The LLM interface stays
       llm.invoke(prompt).content -> str, like every other node, so the
       milestone 6 fake LLM stays one simple class.
       - PLAN_PROMPT asks for one JSON object {"decision", "reason", "steps", 
         "clarifying_question"}.
       - A Pydantic model Plan checks the reply: decision: 
         Literal["answerable","needs_clarification","out_of_scope"], reason: 
         str, steps: list[str] = [], clarifying_question: str | None = None.
       - parse_plan(text, question) -> Plan is a pure function. It strips code
         fences (same idea as extract_sql), then runs Plan.model_validate_json,
         keeps steps[:3], and uses [question] if the plan is answerable but has
         no steps.
       - If the reply is not valid JSON or not a valid Plan, fall back to
         answerable with steps [question] and reason "planner output could not 
         be parsed: <error>". The fallback shows in the trace, and the question
         still goes through the existing SQL path and its guards (validation,
         read-only DB).
       - parse_plan gets plain unit tests this milestone: valid JSON, fenced
         JSON, more than 3 steps, garbage input.
     - Fake LLM in milestone 6: one class that returns scripted strings in
       order, e.g.
       FakeLLM(['{"decision":"answerable","reason":"...","steps":["..."]}', 
       "SELECT ...", "The answer..."]), with .invoke(prompt) returning an object
       with .content and recording the prompt. To return a Plan, it just
       returns that JSON string. No special support for structured output is
       needed.
     - Prompt (prompts.PLAN_PROMPT) gets schema + notes + question +
       clarification (if any). Rules:
       - out_of_scope: asks to change data (insert/update/delete/drop...), or
         unrelated to this database's schema.
       - needs_clarification: only when the question is vague in itself (a
         subjective word like "best" with no measure). NOT for duplicate names
         or several matching records — those are answered by listing all with
         ids.
       - steps: 1 step unless a later part needs an earlier result, or the
         question has separate parts. Each step is self-contained, keeps the
         user's filters exactly (don't add or drop a semester etc., same rule as
         [[retry-must-preserve-meaning]]), and later steps refer to "the result
         of step N".
       - If a clarification is already given, don't ask again.
     - Returns {"plan": ..., "steps": ...}.

     Clarification with interrupt (nodes.ask_user)

     - Separate node with no LLM call: reply = 
       interrupt(state["plan"]["clarifying_question"]) → {"clarification": 
       reply} → edge back to plan.
       Why separate: on resume LangGraph re-runs the interrupted node from the
       top. If interrupt sat inside plan, the LLM would be called again and
       might decide differently.
     - Routing after_plan: answerable → generate_sql; needs_clarification and no
       clarification yet → ask_user; otherwise (out_of_scope, or still unclear
       after one reply) → decline.
     - decline node: answer = short message from prompts (OUT_OF_SCOPE_ANSWER
       with the reason, or the clarifying question), status rejected /
       needs_clarification. No SQL.
     - Checkpointer: build_graph(..., checkpointer=None) compiles with
       checkpointer or InMemorySaver() (ships with langgraph 1.2.22, no new
       package). thread_id = run_id.

     Complexity verdict: modest, not "much more complex". Cost is ~1 small node,
     a checkpointer line, and a resume loop in run_traced (~15 lines). The one
     real trap (node re-execution on resume) is avoided by the separate ask_user
     node. Recommend doing it.

     Multi-step loop

     - check_result on accept also returns step_index: state["step_index"] + 1.
     - after_check: error → retry_or_give_up; step_index < len(steps) →
       generate_sql; else → answer.
