       FK department_id → departments

     Table: students
     One-liner: People who enroll in course offerings.
     Columns: id, name, email, enrollment_year
     Keys / constraints: PK id; name NOT NULL (not unique); email UNIQUE NOT
     NULL;
       CHECK enrollment_year BETWEEN 2000 AND 2100
     ────────────────────────────────────────
     Table: courses
     One-liner: The catalogue: a subject that can be taught many times.
     Columns: id, code, title, credits, department_id

     >

     One-liner: Teaching periods.
     Columns: id, name, year, term, start_date, end_date
     Keys / constraints: PK id; name UNIQUE (e.g. Fall 2025); term CHECK IN
       ('Spring','Fall'); UNIQUE(year, term); CHECK start_date < end_date
     ────────────────────────────────────────
     Table: course_offerings
     One-liner: A course taught by one teacher in one semester.
     Columns: id, course_id, teacher_id, semester_id

     Table: enrollments

     grade

     Decisions:
     - One name column (full name): users ask by full name, so WHERE name = 
       'Maria Garcia'
       is the simplest SQL for the LLM; concatenating first/last differs per
       database (|| vs
       CONCAT), which would leak DB-specific syntax into generation. id + email
       disambiguate.
     - Grade is numeric 0–100, NULL = not graded yet. Pass mark (60) and
       "current semester" are
       business rules in the config file (milestone 2+), not columns — keeps
       schema DB-agnostic
       and results not dependent on today's date.
     - Every table/column gets a short SQL comment so the schema file explains
       itself.
     - PRAGMA foreign_keys = ON at build time.
