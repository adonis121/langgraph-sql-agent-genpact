     Milestone 4 — Tracing

     Context

     Tracing is mandatory: it must show user input -> graph nodes -> generated
     SQL -> DB results -> final answer.
     Today src/main.py calls graph.invoke(); LangSmith picks up runs from .env
     (LANGSMITH_TRACING,
     LANGSMITH_PROJECT) but runs have default names and no metadata, and nothing
     is saved in the repo.
     Goal: every run gets a findable LangSmith run AND a small local
     traces/<run_id>.jsonl, written by a
     separate tracing module while the graph streams. Nodes stay unchanged.

     Design

     1. src/tracing.py (new, the only place that knows about tracing)

     - run_traced(graph, state, *, model, trace_dir="traces") -> (final_state, 
       run_id, path)
       - run_id = uuid4(); the same id is passed to LangSmith as
         config["run_id"], so the local file
         name equals the LangSmith run id (search it in the UI or open it
         directly).
       - LangSmith config: run_name="university-qa", tags=["sql-agent"],
         metadata={"question", "run_id", "model"}. If LangSmith env vars are
         missing, this config is simply
         ignored by LangChain — no branches needed; the local file is always
         written.
       - graph.stream(state, config, stream_mode=["updates", "values"]):
         - "updates" chunk {node: changes} → write one line
         - "values" chunk → keep the latest as the final state (so we don't
           re-implement the results reducer)
       - Duration: time between consecutive update chunks (time.perf_counter()).
         Each chunk arrives right after
         its node finishes and nodes run sequentially, so this is the node's
         time (plus tiny routing overhead).
       - Lines written and flushed one at a time (open(..., "a")), so a crash
         mid-run still leaves a partial trace.
     - Line format (json.dumps(..., default=str) for dates/Decimals):
       - first: {"run_id", "ts", "event": "start", "question", "model"}
       - per node: {"run_id", "ts", "event": "node", "node", "duration_ms", 
         "changes": {...}}
       - last: {"run_id", "ts", "event": "end", "status", "answer", "total_ms"}
     - compact(changes): any rows list (in last_result and in results entries)
       is cut to the first
       MAX_TRACE_ROWS = 20 and gets "row_count": <total> + "truncated": true
       when cut. Other keys as-is.
       No table/column names in here — it only knows the state keys, so it stays
       DB-agnostic.

     2. src/show_trace.py (new) — python -m src.show_trace traces/<run_id>.jsonl

     Prints a readable timeline: header with question/model/run_id, then one
     block per node
     ([3] validate_sql  2 ms) showing SQL, error, attempts, and rows as a small
     table (reuse
     prompts.format_rows_as_table from src/agent/prompts.py), then status +
     answer + total time.

     3. src/main.py

     ask() uses run_traced(...) instead of graph.invoke(...), passes
     os.getenv("OPENAI_MODEL").
     At the end the CLI prints Run id: ... and Trace: traces/<run_id>.jsonl.

     4. Repo / git

     - .gitignore: traces/*.jsonl (everyday runs ignored).
     - Kept examples: traces/examples/ (tracked), copied by hand from real runs,
       3 files:
       simple-success.jsonl, retry-then-success.jsonl, give-up.jsonl (+ a short
       traces/examples/README.md
       saying which question produced each). Later the debugging bug-trace from
       CLAUDE.md goes here too.
     - No new package (langsmith already in requirements.txt).

     5. Tests (tests/test_tracing.py, no LLM, no graph)

     - compact truncates >20 rows and adds row_count; leaves small results
       unchanged.
     - Writing a trace from a hand-made list of update chunks gives
       start/node/end lines in order, valid JSON.
       (The fake-LLM end-to-end tests stay in their own milestone, as agreed.)

     6. Docs

     Short section in docs/ (e.g. docs/tracing.md): what is traced, where, how
     to read it, example output.

     Example: a run that needed a retry (shown by show_trace)

     Run 7f3c…  model=gpt-4o-mini
     Q: Average grade per course in Fall 2024?

     [1] generate_sql   812 ms  attempts=1
         SELECT c.title, AVG(e.grade) FROM enrollments e JOIN courses c ... 
     WHERE o.semester = 'Fall 2024'
     [2] validate_sql     1 ms  ok (LIMIT 100 added)
     [3] execute_sql      3 ms  ERROR Database error: no such column: o.semester
     [4] generate_sql   790 ms  attempts=2   <- retry, prompt included the error
     above
         SELECT c.title, AVG(e.grade) ... WHERE o.term = 'Fall' AND o.year = 
     2024 ...
     [5] validate_sql     1 ms  ok
     [6] execute_sql      2 ms  6 rows
     [7] check_result     0 ms  accepted (attempts reset to 0)
     [8] answer         640 ms

     status=done  total=2.3 s
     Answer: ...
     (Column names above are illustrative; the real example file comes from an
     actual run.)
     An empty-result retry looks similar: check_result  error=<EMPTY_RETRY_HINT>
     empty_retry_used=true → back to generate_sql.

     Files

     - new: src/tracing.py, src/show_trace.py, tests/test_tracing.py,
       docs/tracing.md, traces/examples/*
     - changed: src/main.py, .gitignore
     - unchanged: all nodes, graph, state

     Verification

     1. pytest — all green (existing + new tracing tests).
     2. python -m src.main "How many students are there?" → prints run id +
        trace path; file has start, 5 node lines, end.
     3. python -m src.show_trace traces/<id>.jsonl → readable timeline.
     4. LangSmith: run named university-qa with tags/metadata, its id = the file
        name.
     5. Run with LANGSMITH_TRACING=false → still works, local file still
        written.
     6. Provoke a retry (a question that commonly triggers a wrong column) and a
        give-up; copy them to traces/examples/.

  What was built
  - src/tracing.py: runs the graph and writes traces/<run_id>.jsonl while it

  - python -m src.show_trace <file>: prints a trace as a numbered timeline with
    SQL, errors, attempts, rows as small tables, and the answer.
  - CLI: now prints the run id, the trace path and the show_trace command to
    view it.
  - Also added: tests/test_tracing.py (no LLM; a fake graph replays stream
    chunks) and docs/tracing.md.
