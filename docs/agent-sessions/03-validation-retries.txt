     Milestone 3 — validation, error handling, retries

     Context

     Milestone 2 runs generate_sql -> execute_sql -> answer in a straight line:
     a bad query
     ends the run with a raw DB error, an empty result is final, and nothing
     checks the SQL
     before it runs. Milestone 3 adds a validate_sql node, a check_result node,
     retries
     that feed the error and the failed SQL back to the model (max 3 attempts
     per step), and a
     give_up node. No planner, tracing or fake-LLM tests yet.

     State (src/agent/state.py, and update the list in CLAUDE.md)

     Two new keys; you picked the flag for the empty retry so results only holds
     good results:
     - empty_retry_used: bool — set by check_result when it uses the one empty
       retry, reset when the step succeeds.
     - last_result: dict | None — {"columns", "rows"} from execute_sql, waiting
       for check_result.
       This one follows from your choice: if execute_sql can't append to
       results, the rows need
       somewhere to wait until check_result accepts them. check_result is now
       the only node that
       appends to results.

     initial_state sets both (False / None). status stays "running" until answer
     ("done")
     or give_up ("error").

     1. validate_sql function — new src/agent/sql_validation.py

     A pure function with no LLM or DB: validate_sql(sql: str, row_limit: int = 
     ROW_LIMIT) -> str.
     It returns the cleaned SQL (LIMIT added) or raises ValueError with a short
     message the
     model can act on. Steps:
     1. Strip whitespace and one trailing ;. Empty → "Query is empty."
     2. Make a copy with string literals and comments blanked out, used only for
        the checks.
        This stops WHERE status = 'DROPPED' or -- delete later from being
        flagged.
     3. Only SELECT/WITH: the first word of the copy must be SELECT or WITH.
     4. Single statement: no ; left in the copy.
     5. No write keywords: whole-word, case-insensitive match on
        INSERT|UPDATE|DELETE|DROP|ALTER|CREATE. \b means created_at doesn't
        match.
     6. LIMIT: if the copy has no LIMIT, append "\nLIMIT {row_limit}". The
        newline matters
        in case the query ends with a -- comment. ROW_LIMIT = 200.

     Known simplification to mention in an interview: the LIMIT check is "LIMIT
     anywhere", so a
     LIMIT inside a subquery counts. LIMIT also isn't universal SQL (SQL Server
     uses TOP); fine
     for SQLite/Postgres/MySQL and noted in docs.

     2. Nodes (src/agent/nodes.py)

     MAX_ATTEMPTS = 3 lives here.
     - generate_sql: returns attempts + 1. When state["error"] is set, it adds
       the
       retry section (failed SQL + error) to the prompt.
     - validate_sql (node): calls the function. Ok → {"sql": cleaned, "error": 
       None}.
       Failure → {"error": "Validation failed: <msg>"}.
     - execute_sql: ok → {"last_result": {...}, "error": None}. Failure →
       {"error": "Database error: <msg>"}, using exc.orig when present so the
       model gets
       no such column: s.gpa and not SQLAlchemy's long wrapper text. It no
       longer sets status.
     - check_result:
       - not empty → append {step_index, step, sql, columns, rows} to results,
         reset
         attempts=0, error=None, empty_retry_used=False, last_result=None.
       - empty and not empty_retry_used and attempts < MAX_ATTEMPTS → {"error": 
         "Empty result: ...", "empty_retry_used": True}. The text comes from
         prompts.EMPTY_RETRY_HINT (see section 4).
         It must not change what the question means. The model may only fix
         mistakes: spelling or
         case of a literal value ('fall 2026' → 'Fall 2026'), a wrong join path,
         the wrong column.
         It must not widen a filter, loosen a comparison (= 100 → >= 90), or
         drop a condition.
         If the query already matches the question, it returns the same query,
         and the second empty
         result is accepted as the real answer.
       - empty otherwise → accept it as a real empty answer (same as the success
         branch).
         A truthful "no records" beats give_up.
     - is_empty_result(rows): not rows, or one row whose values are all None.
       COUNT = 0
       is not empty, because 0 is a real answer.
     - answer: the error branch goes away (answer is only reached on success).
       The empty
       branch uses is_empty_result, so AVG = NULL also gives EMPTY_ANSWER
       without an LLM call.
     - give_up (new, no LLM): {"answer": GIVE_UP_ANSWER.format(...), "status": 
       "error"}.

     3. Routing (src/agent/graph.py)

     def retry_or_give_up(state):   return "generate_sql" if state["attempts"] <
     MAX_ATTEMPTS else "give_up"
     def after_validate(state):     return retry_or_give_up(state) if
     state["error"] else "execute_sql"
     def after_execute(state):      return retry_or_give_up(state) if
     state["error"] else "check_result"
     def after_check(state):        return retry_or_give_up(state) if
     state["error"] else "answer"
     They're wired with add_conditional_edges(..., path_map=[...]) so the drawn
     graph shows
     real edges. Moving to the next step after success waits for the planner
     (milestone 4);
     for now after_check goes to answer.

     4. Prompts (src/agent/prompts.py)

     - RETRY_SECTION: "## Previous attempt (failed)\nSQL:\n{sql}\nProblem:
       {error}\nWrite a corrected query."
       GENERATE_SQL_PROMPT gets a {retry} placeholder (empty string on the first
       attempt).
     - EMPTY_RETRY_HINT (used as the {error} in RETRY_SECTION for empty
       results):
     Empty result: the query ran but returned no rows (or only NULLs).
     This may be the correct answer. Check only for mistakes:
     - a literal value spelled or cased differently from the data (see business 
     rules)
     - a wrong join path or wrong column
     Do NOT change the meaning of the question: never widen, loosen or remove a 
     filter
     (e.g. do not turn "= 100" into ">= 90"). If the query already matches the 
     question,
     return it unchanged.
     - GIVE_UP_ANSWER, EMPTY_ANSWER stay here; ERROR_ANSWER is removed.

     5. Tests — new tests/test_sql_validation.py (no LLM, no DB)

     One test per rule:
     - accepts a plain SELECT; accepts a WITH query
     - rejects non-SELECT (PRAGMA table_info(students))
     - rejects multiple statements (SELECT 1; SELECT 2); allows one trailing ;
     - rejects each write keyword (parametrized over the 6; WITH x AS (...) 
       DELETE ... included)
     - allows keywords inside string literals and as part of names ('DROPPED',
       created_at)
     - adds LIMIT when missing (also after a trailing -- comment); keeps an
       existing LIMIT
     - rejects empty SQL

     Plus a few one-line tests for is_empty_result ([], [(None,)], [(0,)],
     [(None, None)]).

     What the user sees

     - Bad SQL (unknown column, syntax error, or validation reject like two
       statements):
       usually nothing. The error and SQL go back to the model, attempt 2 fixes
       it, and the user
       gets a normal answer. The retry shows in attempts, and in the trace from
       milestone 4.
     - Empty result: one silent retry that may only fix mistakes and keeps the
       question's
       meaning. "Which students got 100?" stays grade = 100. If it's still
       empty:
       "The query returned no matching records." AVG over ungraded enrollments →
       the same message,
       not "the average is None".
     - 3 failed attempts → give_up:
     Sorry, I couldn't answer this question after 3 attempts.
     Last SQL tried:
       SELECT s.name, s.gpa FROM students s ...
     Last error: Database error: no such column: s.gpa
     Try rephrasing the question or naming the table/field you mean.
       Only the last SQL and error are in the state; all attempts go in the
       trace in milestone 4.

     Why the keyword check alone isn't security

     - It's a text denylist, so it's incomplete by design. SQLite has other ways
       to change things
       or reach outside the DB that aren't on the list: REPLACE, ATTACH 
       DATABASE, PRAGMA
       writes, VACUUM INTO, load_extension(). Other dialects add more (COPY,
       GRANT,
       MERGE, SELECT ... INTO, side-effecting functions). A list can't keep up
       with every dialect.
     - Text matching is fragile both ways: it can block valid names or literals,
       and it can miss
       obfuscated input. It doesn't understand SQL.
     - It does nothing about cost: a SELECT with a cross join can still scan a
       lot, because
       LIMIT caps output rows, not work.
     - What actually protects us is the database. The file is opened with
       mode=ro (SQLite
       itself refuses writes) plus PRAGMA query_only = ON (already in
       src/db/database.py:17,
       tested in tests/test_database.py). Even SQL that passes validation can't
       write. In
       production that would be a SELECT-only DB user on a read replica, a
       statement timeout, and
       only the views/tables the agent should see.
     - So the validator's real job is to fail fast with a clear message the
       model can fix and to
       keep results bounded. It's a guardrail for correctness, not the security
       boundary.
       I'll write this up in docs.
